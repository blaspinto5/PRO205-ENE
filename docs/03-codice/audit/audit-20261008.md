# Auditoría de PRO205–ENE

**Fecha:** 8 de octubre de 2026. **Casos:** Huellitas, Tecnobox e Instituto Códice. **Tipo:** auditoría documental, de código y de ejecución local. **Resultado:** los productos académicos principales existen y las comprobaciones realizadas pasan; el cierre global del plan maestro todavía tiene brechas de historial, validación de entrega y evidencia personal.

## 1. Dictamen

El proyecto ya contiene una aplicación Códice implementada, fuentes editables, pruebas y entregables de los tres casos. No encontré un producto principal ausente en Huellitas o Tecnobox. Códice supera los mínimos cuantitativos de requisitos, clases, pruebas y funciones de la rúbrica disponible.

Volví a compilar: **0 errores y 0 advertencias**. Volví a ejecutar las suites: **55 casos aprobados, 0 fallidos, 0 omitidos**. Comprobé el arranque del paquete entregado y regeneré sus doce vistas WPF en una copia aislada, con cero errores de binding. Los cuatro ensamblados principales republicados con el mismo perfil coinciden con la entrega.

No corresponde concluir «100 % cumplido» ni asignar una nota: faltan historial Git real, aceptación en otro Windows limpio, registro de interacción manual y comprobación personal de la defensa. Los tres criterios transversales suman **28 %** y requieren valoración del proceso y del estudiante. Los artefactos dan respaldo, pero no certifican por sí solos autonomía ni desempeño sobresaliente.

## 5. Hallazgos y prioridades

**P1:** resolver antes de declarar aceptación completa. **P2:** corregir o confirmar antes de presentar. **P3:** mejora de mantenibilidad; no bloquea por sí sola la entrega académica. Ningún P0 ni fallo funcional bloqueante apareció en las pruebas ejecutadas.

### A01 · P1 · Git no conserva ninguna versión

**Hecho:** `git status --short` muestra los directorios/archivos del proyecto sin seguimiento; `git log` indica que main no tiene commits; no existe remoto.

**Fuente:** estado actual y plan maestro, líneas 857, 891–893: exige cambios pequeños e historial de evolución; prohíbe limitarse a un único commit final.

**Consecuencia:** no existe historial Git que sustente revisiones o permita volver a una versión. Los ZIP proporcionan copias de entrega, pero no evolución. Es una brecha real del plan maestro; no una exigencia literal de GitHub en la rúbrica.

**Prioridad:** registrar una versión base revisada con fecha real, luego cambios coherentes. No inventar commits antiguos ni presentar un primer commit actual como el historial previo. Publicar GitHub requiere definir destino; esta auditoría no lo publica.

### A02 · P1 · Otro Windows limpio sigue sin comprobarse

**Hecho:** `CleanMachineVerified = false` en la evidencia original. La auditoría confirma autocontención y arranque en este mismo equipo, no compatibilidad con otra instalación.

**Fuente:** `docs/03-codice/test-evidence/current/portable-startup.json`, cierre de fase 6 y checklist portable, línea 66.

**Consecuencia:** permanecen abiertas dependencias del SO, resolución/DPI y condiciones del computador receptor.

**Cierre verificable:** ejecutar el ZIP exacto en otro Windows x64 compatible sin SDK/runtime de desarrollo; registrar versión del SO, resolución/DPI, hash del ZIP, arranque, operaciones, cierre/reapertura y recuperación de respaldo. Es aceptación práctica de portabilidad; no demuestra que falte el ejecutable solicitado por 3D.

### A03 · P1 · Falta registro de interacción manual completa

**Hecho:** DesktopTests invoca comandos y ViewModels; UiPreview prepara/renderiza controles. El chat previo y la nota de portafolio reconocen el recorrido manual pendiente.

**Consecuencia:** los resultados no verifican tabulación, teclado, selección real, scroll, cambio de pantallas durante operaciones ni mensajes de sistema por interacción humana.

**Cierre verificable:** acta breve con datos ficticios: crear/editar estudiante y asignatura; curso/matrícula/eventos; registrar y corregir nota/asistencia; rechazar duplicados/nota inválida; ambos informes; cerrar/reabrir; respaldo/restauración. Registrar resultado y hallazgos reales.

### A04 · P2 · Checklists y estado final se contradicen

**Hecho:** `portable-architecture.md`, líneas 68–74, conserva siete casillas pendientes sobre rutas, recuperación, traslado, permisos, backup, limpieza y manual. Su cierre, línea 83, afirma comprobación. `phase-checklists.md`, línea 87, marca los once criterios «sin brechas de Sobresaliente», aunque Git y la evaluación personal siguen pendientes.

**Consecuencia:** el lector debe decidir qué estado creer. Las notas históricas son útiles, pero deben identificarse como historia; una casilla de aceptación vigente no debería contradecir su evidencia.

**Cierre:** una tabla vigente de estado/evidencia/fecha/alcance, manteniendo otro Windows y manual pendientes hasta realizarlos. Para transversales, usar «evidencia preparada, valoración docente pendiente» en vez de certificarlos por checklist.

### A05 · P2 · La herramienta portable declara verificación visual sin realizarla

**Hecho:** `tools/verify-portable.ps1`, línea 82, asigna `VisualInterfaceVerified = true` de forma fija. Sus acciones comprueban hashes, arranque, bloqueo, permiso y traslado; no inspeccionan las vistas ni el archivo de errores de binding.

**Consecuencia:** una futura publicación podría recibir esa bandera aunque cambie la UI y no se haya renderizado/revisado. La UI actual sí tiene evidencia independiente y nueva comprobación; el hallazgo afecta la confiabilidad del indicador automático.

**Cierre:** retirar esa afirmación del verificador portable o condicionarla a evidencia UI comprobada y vinculada al paquete exacto. Separar arranque, render, revisión visual e interacción manual.

### A06 · P2 · Falta demostrar la defensa final y el aporte personal

**Hecho:** existen defensas de Huellitas, Tecnobox y fases 4/5. No hay una defensa específica completa de fase 6 dentro de docs. La nota independiente aporta preparación y reconoce ese pendiente.

**Riesgo:** el estudiante puede tener los artefactos sin poder explicar una decisión, interpretar una prueba o modificar un flujo; esto afecta especialmente habilidades personales/sociales.

**Cierre:** guion y ensayo de fase 6, demostrando un flujo de punta a punta y un cambio pequeño. Distinguir decisiones propias, ayuda recibida y verificaciones realizadas. La defensa escrita de fase 6 es material de apoyo propuesto, no un producto adicional explícito de 3D.

### A07 · P2 · Condiciones finales del docente no disponibles

**Hecho:** el enunciado remite al docente/aula para modalidad, fechas y aspectos concretos del sello. No encontré en la carpeta instrucciones que los confirmen. Los PDF revisados identifican caso/asignatura, pero no constituyen una presentación individual completa con autor, sección, docente y fecha de entrega.

**Cierre:** cotejar rúbrica/plantilla vigente y formato solicitado; incorporar identificación si corresponde. Recuperar capturas originales de 1.8/1.9 o el documento oficial para cerrar el límite de procedencia. No inventar un plazo, un docente ni normas de uso de IA.

### A08 · P3 · Los generadores de PDF quedaron fuera de las fuentes entregadas

**Hecho:** encontré `build_huellitas.py`, `build_tecnobox.py`, `build_codice.py`, `build_codice_implemented.py` y `build_manual.py` bajo `.tools/work/`. `.gitignore` excluye `.tools`; el empaquetador no la incorpora.

**Consecuencia:** los PDF y editables existen, pero la regeneración exacta de esos PDF no está incluida en el ZIP de fuentes. No falta el entregable académico; falta reproducibilidad del proceso.

**Cierre:** conservar generadores útiles en una ubicación de herramientas de documentación, con instrucciones mínimas y dependencias. Evitar añadir runtimes o archivos temporales al repositorio.

### A09 · P3 · La presentación conoce una excepción de EF Core

**Hecho:** `ScreenViewModel.cs`, líneas 3 y 58, importa EntityFrameworkCore y trata `DbUpdateException`. ADR-02 describe uso de Infrastructure únicamente en la composición inicial.

**Consecuencia:** no hay reglas académicas ni DbContext en el ViewModel, pero sí acoplamiento de presentación al proveedor de persistencia. Cambiar almacenamiento obliga a ajustar esa traducción.

**Mejora:** traducir fallos de persistencia a errores de aplicación en el límite correspondiente. No reestructurar todo el prototipo por este detalle.

### A10 · P3 · Carga y guardado recorren todo el catálogo

**Hecho:** los servicios buscan un curso mediante `GetAllAsync`; `SqliteRepositories.GetAllAsync` carga todos los cursos y sus grafos. SaveAsync(Course), líneas 53–57, consulta todos los IDs de varias tablas. Workspace reconstruye el snapshot tras cada operación.

**Riesgo:** costo de consulta/guardado creciente con cursos, matrículas y registros. No medí un incumplimiento de rendimiento y el catálogo no fija un volumen ni tiempo objetivo.

**Mejora condicionada:** si crece el uso, definir escenario y medir; luego consultas por ID y por alcance. No declarar que la eficiencia institucional está certificada porque los ejemplos pequeños funcionan.

## 6. Límites de seguridad e integridad

El código protege invariantes, normaliza claves, conserva IDs, valida fechas/notas, impide duplicados, usa claves foráneas/checks y transacción al guardar el curso. Las pruebas de SQLite incluyen reversión de un grafo inválido, recuperación, correcciones, traslado de datos cerrados e integridad. El bloqueo de archivo limita una instancia por carpeta.

El alcance adoptado es **académico local, con datos ficticios y una cuenta Windows controlada**. No hay login, roles ni cifrado, y eso está acordado y documentado. Quien accede a los archivos puede copiar/modificar SQLite. Las marcas de última modificación no reconstruyen todo el historial. Tampoco todos los invariantes entre cursos se imponen mediante constraints SQL: las reglas dependen de utilizar los casos de uso previstos.

Estos son límites reales de operación, no productos faltantes automáticamente exigidos por la rúbrica. Antes de usar datos reales, multiusuario o una red compartida, se necesita otra definición de requisitos y validación. No realicé una revisión jurídica ni afirmo cumplimiento normativo vigente; las reglas académicas se auditan como decisiones explícitas del prototipo.
